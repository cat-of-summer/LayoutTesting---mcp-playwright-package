# Фаза 0. Подготовка

Стенд, связность с проектом, доступ к Figma, две сессии и правила проекта — до первой строки кода.

## Чек-лист

ВХОД: есть ссылки на кадры макета и путь к проекту.
ШАГИ:
  1. stand_info — версия, поднятые группы, guide.available: true (иначе — сообщить человеку).
  2. figma_status с figma: <ссылка на кадр> - editor.state, rest.configured, file.editor.state, rest.tier1; rest: false → action: token сам, без вопроса; editor.state: needs_human → ссылку editor.handoff.url человеку; выпуск упал → вопрос человеку; file.editor.state: view_only → копию в черновики стенд сделает сам на первом figma_* (команда из FIGMA_DUPLICATE_TEAM или выбор человека в форме); отказ или клиент без форм → вопрос человеку до вёрстки: edit-доступ, команда для duplicate или работа руками.
  3. dev-сервер на 0.0.0.0 → browser_goto http://host.docker.internal:<порт> отвечает 200.
  4. browser_open второй раз с animations: "allow" — живая сессия; обе с keepAlive: true и держать до конца.
  5. README, CLAUDE.md, конфиг сборщика — как подключаются ассеты, что делает CSS-фреймворк с p и h1..h6; словарь его утилит: зона клика, иконки, видимость.

## 0.1 Стенд и доступ

```
stand_info                     → версия, поднятые группы инструментов, пресеты viewport, guide
help(topic: "figma")           → входная точка регламента
figma_status с figma: <кадр>   → живы ли канал редактора и REST, и открывается ли редактору этот файл
```

`stand_info.guide.available: false` значит, что образ собран без регламента. Это ошибка сборки —
сказать человеку сразу, а не работать по встроенному минимуму молча.

**REST нужен до снимка, а не «когда понадобится».** Комментарии к макету есть только в REST, а в
них живёт половина требований («здесь JS-анимация по ховеру, как на сайте-эталоне»). `rest.configured:
false` → `figma_status` с `action: token` — сразу, не спрашивая: логин и пароль в .env стенда
заданы ровно для этого, токен только на чтение. Figma попросила капчу, код 2FA или подтверждение
из письма (`editor.state: needs_human`) — ссылку `editor.handoff.url` отдать человеку: там живой
экран браузера стенда, проверку он проходит сам, стенд сохранит вход; затем снова `action: token`.
Не выпустился по другой причине → вопрос человеку. Отсутствие токена -
блокер фазы 2, а не пропуск: на одном лендинге комментарии не читали ни разу, и hover трёх
блоков был придуман вместо взятого из комментария.

**Вход в редактор - ещё не доступ к файлу.** `editor.state: ready` говорит только о том, что
стенд залогинен. Открывается ли редактору сам макет, видно в `file` ответа `figma_status` с
`figma`. `file.editor.state: view_only` значит, что аккаунту стенда файл открыт только на просмотр:
Plugin API в этом режиме Figma не даёт, и канал редактора для файла не заработает, сколько ни
повторять. REST на месте View - двадцать запросов к файлам в месяц на все проекты (`rest.tier1`),
это одна-две задачи. Если и он выбран, `figma_*` не работают вовсе. Выходы, по убыванию пользы:

1. edit-доступ аккаунту стенда от владельца файла - тогда работает всё;
2. копия в черновики команды аккаунта стенда, если владелец разрешил копирование. Её делает сам
   первый `figma_*`, который пойдёт в файл: команда берётся из `FIGMA_DUPLICATE_TEAM` в .env
   стенда, а без неё человек выбирает её в форме клиента - агенту ничего делать не надо, в ответе
   останется `copy` с пометкой "снято с копии". Клиент без форм или отказ человека - явный
   `figma_sync` с `duplicate: "<команда>"` после вопроса человеку (`duplicate: ""` вернёт список
   команд). Дизайнер правит оригинал, а не копию: `copy.stale` в ответах - пора копировать заново;
3. ни то ни другое - канал ui: `figma_inspect` и `figma_export` с `channel: "ui"` снимают значения
   с панели свойств интерфейса Figma и выгружают кнопкой Export, сверка - `figma_compare` с `image`
   (PNG из `figma_export`). `channel: "auto"` переходит на ui сам. Остальные `figma_*` работают по
   снимку, и без него их нет: структуру собирать по дереву `figma_inspect` с `depth`.

Выбор между ними - вопрос человеку до вёрстки, а не обнаружение посреди работы: в отзыве, ради
которого написан этот раздел, три вызова ушли на `timeout` редактора, прежде чем причина нашлась
по скриншоту.

## 0.2 Связность стенда с проектом

Стенд работает в контейнере и **не видит `localhost` хоста**. Поднять проект и сразу проверить
доступность:

```
dev-сервер на 0.0.0.0  →  browser_goto http://host.docker.internal:<порт>
```

Для Vite и Astro дополнительно `server.allowedHosts: ['host.docker.internal']`, иначе 403. У
Astro `allowedHosts` для `preview` берётся из `server`, а не из `vite.server`.

> Почему первым шагом. Выяснение этого в середине работы стоило пяти вызовов подряд:
> `ERR_CONNECTION_REFUSED` → IP моста → 403 → догадка. Проверка стоит один вызов, если сделать
> её до вёрстки. Подробности адресации — `help(topic: "addressing")`.

## 0.3 Две сессии с самого начала

Рабочая сессия открывается с замороженным движением: снимки и замеры в ней воспроизводимы, но
hover, intro-анимации и переходы в ней **не видны** — стенд глушит их `!important` и
закрепляет проявившиеся по прокрутке блоки (`data-lt-pinned`). Об этом говорит `motionNote` в
ответе `browser_open` и `browser_goto`.

Поэтому вторая сессия — живая, `animations: "allow"` — открывается **сразу** и живёт параллельно.
В ней проверяют каждый hover, стартовую анимацию (`browser_goto` с `frames`), модалки и
`interaction_audit`.

Обе сессии открываются с `keepAlive: true`. Без него сессия закрывается после 15 минут простоя, а
между проверками пишется код — мобильная сессия закрылась между двумя сверками, и об `keepAlive`
узнали из текста ошибки.

> Как здесь ошибаются. Живую сессию открыли под конец и проверили точечно. В рабочей hover
> перекрывающихся элементов выглядел нормально; в живой оказалось, что наведённый элемент
> перескакивает по z-index и порядок наложения дёргается на границе. Стартовая анимация хиро показывала
> финальный кадр до старта JS — в замороженной сессии это невидимо по определению.

## 0.4 Правила проекта

Прочитать `README.md`, `CLAUDE.md`, конфиг сборщика. Понять:

- как шаблон подключает ассеты, иконки и шрифты — плагин, алиасы, соглашение;
- какие компоненты трогать нельзя, потому что они общие для всех проектов;
- что делает CSS-фреймворк проекта с базовыми элементами;
- **словарь фреймворка**: какие его утилиты отвечают за зону клика, маски иконок, видимость, сетку.
  Выписать коротко — по нему на фазе 3 сверяется UI-кит.

> Зачем. Фреймворк стилизовал `p` и `h1..h6` напрямую через element-селекторы. `font-size` на
> родителе не наследовался — проигрывал element-правилу. Полчаса на поиск «почему 17px вместо
> 32px».

## Гейт фазы

Страница проекта открывается через `browser_goto`; макет снимается хотя бы одним каналом - редактор
для этого файла (`file.editor.usable`), копия в черновиках или REST с остатком - либо работа
через канал ui (только `figma_inspect` и `figma_export`) согласована с человеком; открыты рабочая и живая сессии с `keepAlive: true`;
известно, куда класть ассеты и как они подключаются.
