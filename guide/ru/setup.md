# Фаза 0. Подготовка

Стенд, связность с проектом, доступ к Figma, две сессии и правила проекта — до первой строки кода.

## Чек-лист

ВХОД: есть ссылки на кадры макета и путь к проекту.
ШАГИ:
  1. stand_info — версия, поднятые группы, guide.available: true (иначе — сообщить человеку).
  2. figma_status — editor.state и rest.configured; rest: false → action: token, не вышло → вопрос человеку.
  3. dev-сервер на 0.0.0.0 → browser_goto http://host.docker.internal:<порт> отвечает 200.
  4. browser_open второй раз с animations: "allow" — живая сессия; обе держать до конца.
  5. README, CLAUDE.md, конфиг сборщика — как подключаются ассеты, что делает CSS-фреймворк с p и h1..h6.

## 0.1 Стенд и доступ

```
stand_info              → версия, поднятые группы инструментов, пресеты viewport, guide
help(topic: "figma")    → входная точка регламента
figma_status            → живы ли канал редактора и REST
```

`stand_info.guide.available: false` значит, что образ собран без регламента. Это ошибка сборки —
сказать человеку сразу, а не работать по встроенному минимуму молча.

**REST нужен до снимка, а не «когда понадобится».** Комментарии к макету есть только в REST, а в
них живёт половина требований («здесь JS-анимация по ховеру, как на сайте-эталоне»). `rest.configured:
false` → `figma_status` с `action: token`; не выпустился → вопрос человеку. Отсутствие токена —
блокер фазы 2, а не пропуск: на одном лендинге комментарии не читали ни разу, и hover трёх
блоков был придуман вместо взятого из комментария.

## 0.2 Связность стенда с проектом

Стенд работает в контейнере и **не видит `localhost` хоста**. Поднять проект и сразу проверить
доступность:

```
dev-сервер на 0.0.0.0  →  browser_goto http://host.docker.internal:<порт>
```

Для Vite и Astro дополнительно `server.allowedHosts: ['host.docker.internal']`, иначе 403. У
Astro `allowedHosts` для `preview` берётся из `server`, а не из `vite.server`.

> Почему первым шагом. Выяснение этого в середине работы стоило пяти вызовов подряд:
> `ERR_CONNECTION_REFUSED` → IP моста → 403 → догадка. Проверка стоит один вызов, если сделать
> её до вёрстки. Подробности адресации — `help(topic: "addressing")`.

## 0.3 Две сессии с самого начала

Рабочая сессия открывается с замороженным движением: снимки и замеры в ней воспроизводимы, но
hover, intro-анимации и переходы в ней **не видны** — стенд глушит их `!important` и
закрепляет проявившиеся по прокрутке блоки (`data-lt-pinned`). Об этом говорит `motionNote` в
ответе `browser_open` и `browser_goto`.

Поэтому вторая сессия — живая, `animations: "allow"` — открывается **сразу** и живёт параллельно.
В ней проверяют каждый hover, стартовую анимацию (`browser_goto` с `frames`), модалки и
`interaction_audit`.

> Как здесь ошибаются. Живую сессию открыли под конец и проверили точечно. В рабочей hover
> перекрывающихся элементов выглядел нормально; в живой оказалось, что наведённый элемент
> перескакивает по z-index и порядок наложения дёргается на границе. Стартовая анимация хиро показывала
> финальный кадр до старта JS — в замороженной сессии это невидимо по определению.

## 0.4 Правила проекта

Прочитать `README.md`, `CLAUDE.md`, конфиг сборщика. Понять:

- как шаблон подключает ассеты, иконки и шрифты — плагин, алиасы, соглашение;
- какие компоненты трогать нельзя, потому что они общие для всех проектов;
- что делает CSS-фреймворк проекта с базовыми элементами.

> Зачем. Фреймворк стилизовал `p` и `h1..h6` напрямую через element-селекторы. `font-size` на
> родителе не наследовался — проигрывал element-правилу. Полчаса на поиск «почему 17px вместо
> 32px».
