# Стенд тестирования вёрстки

Проверяет сайты браузером: снимает скриншоты, находит поехавшую вёрстку, битые картинки,
проблемы доступности и метрики. Работает как MCP-сервер — ИИ-агент пользуется им сам, — и как
обычная команда в терминале.

---

## Установка из готового образа

Весь стенд — nginx, MCP-сервер и валидатор разметки — запечён в один образ. Разворачивание
сводится к `docker pull`. Если хотите дорабатывать сам стенд, ставьте
[из исходников](#установка-из-исходников).

Нужен Docker, общая сеть и роутер — шаг [«Общая сеть и роутер»](#1-общая-сеть-и-роутер)
одинаков для обоих способов.

Дальше нужны только два файла:

```sh
mkdir -p ~/layout && cd ~/layout
base=https://github.com/cat-of-summer/LayoutTesting---mcp-playwright-package/releases/latest/download
curl -fsSL -o docker-compose.yml "$base/docker-compose.yml"
curl -fsSL -o .env               "$base/.env.example"
docker compose up -d
```

Файлы берутся из релиза, а не из ветки: они генерируются при сборке и в git не лежат.
Релиз выпускается тем же тегом, что и образ, поэтому compose и образ всегда одной версии —
из ветки они могли разъехаться.

Первый запуск качает образ: внутри три браузерных движка, поэтому он большой. Готово,
когда `docker compose ps` показывает `healthy`.

```sh
curl http://127.0.0.1:8089/health
docker compose exec layout lt audit --url http://127.0.0.1/fixtures/broken.html --checks all
```

Второй командой стенд проверяет собственную тестовую страницу с заложенными дефектами и
должен найти их все.

Внутри бандла сервисы делят сетевое пространство, поэтому **свои** страницы открываются по
`http://127.0.0.1/...`, а не по имени контейнера. Чужие проекты — по-прежнему по имени их
контейнера, как в таблице [«Что дать агенту проверять»](#что-дать-агенту-проверять).

Настройки — в `.env` рядом с `docker-compose.yml`:

| Параметр | Зачем менять |
|---|---|
| `NGINX_EXTERNAL_ACCESS` | порт отчётов на хосте, по умолчанию `8089` |
| `MCP_ACCESS` | порт MCP напрямую, мимо nginx |
| `VNU_EXTERNAL_ACCESS` | порт валидатора |
| `NGINX_TRAEFIK_DOMAIN` | домен стенда, по умолчанию `layout.localhost` |
| `VNU_TRAEFIK_DOMAIN` | домен валидатора, по умолчанию `vnu.localhost` |
| `INSTANCE` | суффикс имён — чтобы поднять несколько стендов рядом |
| `BUNDLE_IMAGE` | другой тег образа вместо `:latest` |

`PLAYWRIGHT_SHM_SIZE` в файле нет, но compose его читает: если Chromium падает на длинных
страницах, допишите строкой `PLAYWRIGHT_SHM_SIZE=4gb` (по умолчанию 2 ГБ).

Отчёты и эталоны лежат в томах `artifacts` и `baselines` — они переживают `docker pull`.

## Установка из исходников

Нужен Docker. Проверьте, что демон запущен:

```sh
docker info
```

### 1. Общая сеть и роутер

Стенд живёт в сети `network` вместе с тестируемыми проектами. Если вы уже пользуетесь
[docker_toolkit](https://github.com/cat-of-summer/docker_toolkit), они подняты — пропустите шаг.

```sh
cd network  && cp .env.example .env && docker compose up -d
cd ../traefik && cp .env.example .env && docker compose up -d
```

Проверка: `docker ps` показывает `network_handler` и `traefik`.

### 2. Валидатор разметки

```sh
cd ../vnu && cp .env.example .env && docker compose up -d
```

### 3. Сам стенд

```sh
cd ../app && cp .env.example .env && docker compose up -d --build
```

Первый запуск идёт несколько минут: качается образ с браузерами и ставятся зависимости.
Следите за прогрессом:

```sh
docker compose logs -f playwright
```

Готово, когда в логе появилось `команда lt готова` и `streamable http на 0.0.0.0:8931/mcp`.

### 4. Проверка

```sh
curl http://127.0.0.1:8089/health
docker compose exec playwright lt audit --url http://nginx_layout/fixtures/broken.html --checks all
```

Второй командой стенд проверяет собственную тестовую страницу, в которую намеренно заложены
дефекты. Он должен найти их все — это и есть проверка, что установка удалась.

## Подключение к ИИ-агенту

### Claude Code

```sh
claude mcp add --transport http layout http://127.0.0.1:8089/mcp
```

Проверьте, что подключилось: `claude mcp list` — в списке появится `layout`.

Дальше агенту достаточно сказать словами:

> Проверь вёрстку http://nginx_myshop/ на мобильном и десктопе, покажи что сломано

Агент сам выберет инструменты, снимет скриншоты и вернёт разбор.

### Другие клиенты

Стенд отдаёт стандартный MCP по двум транспортам.

**HTTP** (рекомендуется — браузеры остаются тёплыми между вызовами):

```json
{
  "mcpServers": {
    "layout": { "type": "http", "url": "http://127.0.0.1:8089/mcp" }
  }
}
```

**stdio** (процесс на каждую сессию):

```json
{
  "mcpServers": {
    "layout": {
      "command": "docker",
      "args": ["compose", "-f", "/полный/путь/к/app/docker-compose.yml",
               "exec", "-T", "playwright", "npm", "run", "mcp:stdio"]
    }
  }
}
```

## Что дать агенту проверять

Стенд ходит по сети Docker, поэтому адрес — это **имя контейнера**, а не `localhost`.

| Что проверяем | Адрес |
|---|---|
| Проект из docker_toolkit | `http://nginx_myshop/` |
| Свой файл | положить в `app/data/fixtures/`, открывать `http://nginx_layout/fixtures/имя.html` |
| Dev-сервер на вашей машине | `http://host.docker.internal:5173` |
| Сайт в интернете | обычный адрес, `https://example.com` |

Узнать имя контейнера: `docker ps`.

**Проект в своей сети.** Если тестируемый проект поднят с другим `NETWORK`, подключите к ней
стенд одной командой:

```sh
docker network connect network_cryptodb playwright_layout
```

## Работа руками, без агента

Внутри контейнера доступна команда `lt`. Все примеры ниже запускаются из папки `app` и
обращаются к сервису `playwright` — так устроена сборка из исходников. Если стенд поднят
[из готового образа](#установка-из-готового-образа), сервис называется `layout`, а команды
запускаются из папки с его `docker-compose.yml`:
`docker compose exec layout lt ...`.

**Посмотреть, что вообще есть:**

```sh
docker compose exec playwright lt          # полная справка по флагам
docker compose exec playwright lt info     # пути, адреса, пресеты
```

**Снять скриншот:**

```sh
docker compose exec playwright lt shot --url http://nginx_myshop/ --viewport mobile
```

Ссылка на снимок печатается в ответе — открывается в браузере.

**Проверить страницу целиком:**

```sh
docker compose exec playwright lt audit --url http://nginx_myshop/ --checks all
```

**Следить, чтобы вёрстка не поехала после правок:**

```sh
# первый запуск запоминает эталон
docker compose exec playwright lt compare --url http://nginx_myshop/ --name main

# после правок — сравнение; печатает процент расхождения и ссылку на карту отличий
docker compose exec playwright lt compare --url http://nginx_myshop/ --name main

# если изменения задуманы — обновить эталон
docker compose exec playwright lt compare --url http://nginx_myshop/ --name main --update
```

**Проверить сразу во всех условиях:**

```sh
docker compose exec playwright lt matrix --url http://nginx_myshop/ \
  --viewports mobile,tablet,desktop --schemes light,dark
```

В конце печатается ссылка на HTML-отчёт: карточки со скриншотами всех сочетаний рядом.

**Зайти внутрь:**

```sh
docker compose exec playwright bash
```

`lt` возвращает код `1`, если нашёл проблемы — годится для CI.

## Что стенд умеет находить

**Вёрстка** — горизонтальный скролл, элементы за краем экрана, наложение текста на текст,
текст под непрозрачным слоем, обрезанный текст, `z-index` на `position: static` (задан, а
не работает), битые картинки, картинки без размеров (из-за них прыгает страница), слишком
мелкие кнопки и ссылки, недостаточный контраст.

**Доступность** — два независимых движка правил WCAG: axe-core и pa11y.

**Скорость и прыжки** — CLS, LCP, полный отчёт Lighthouse. CLS показывает, какие именно
блоки сдвинули страницу при загрузке.

**Разметка** — валидатор W3C: незакрытые теги, дубли `id`, обязательные атрибуты.

**Ошибки** — упавшие запросы, 404, ошибки JavaScript. Если что-то из этого случилось,
в ответе перехода и снимка приходит `warnings` со счётчиком: смотреть подробности —
`page_logs`.

**Сравнение с эталоном** — попиксельное, с картинкой отличий.

**SEO** — заголовок и описание с длинами, `canonical` с проверкой саморефренса, `hreflang`
и `x-default`, robots-мета и заголовок `X-Robots-Tag`, Open Graph и Twitter, дерево заголовков
с пропущенными уровнями и лишними `h1`, инвентарь ссылок (внутренние, внешние, `nofollow`,
пустой анкор, `target="_blank"` без `rel="noopener"`), покрытие `alt`, микроразметка — JSON-LD,
микроданные и RDFa. Отдельным полем — `indexable` с перечислением причин, по которым страница
не попадёт в индекс. Оценка SEO из Lighthouse считалась и раньше, но в сводку не попадала;
теперь попадает и влияет на вердикт.

Полный список инструментов агент видит сам; человеку — `lt` без аргументов.

## Работа по сохранённой копии

Разбирать страницу обычно приходится не один раз: снять разметку, посмотреть стили, сделать
снимок, проверить валидатором. Каждый такой шаг — новый поход на чужой сервер. `page_save`
снимает страницу один раз и кладёт её в локальное зеркало, дальше работа идёт по копии.

```sh
# сохранить и получить ссылку на копию
page_save --url https://example.ru/catalog

# то же прямо при переходе в открытой сессии
browser_goto --url https://example.ru/catalog --save
```

В каталоге прогона оказываются две версии страницы, и это не избыточность:

- `raw.html` — то, что отдал сервер: до выполнения скриптов и до переписывания ссылок. По нему
  валидирует `validate_html`, и по нему видно, что получает поисковый робот, не исполняющий JS.
- `page.html` — отрендеренный DOM, ссылки переписаны на локальные копии. Это то, что открывается.

Расхождение между ними — само по себе находка: значит, контент появляется только после JS.

Ресурсы (CSS, картинки, шрифты) складываются рядом с дедупликацией по содержимому: один и тот же
файл, отданный по трём разным адресам, ложится на диск однажды. Скрипты по умолчанию вырезаются —
на копии аналитика стучала бы в сеть, от которой мы и уходили, а роутер SPA подменял бы страницу
пустым каркасом. Разметка JSON-LD при этом сохраняется: это данные, а не поведение.

Копия открывается как обычная страница, и к ней применимы **все** остальные инструменты:

```sh
browser_goto --url <internalUrl копии>   # именно internalUrl, см. «Где лежат результаты»
layout_audit --session ...
screenshot   --session ...
```

Зеркала лежат в `app/data/sites/` и, в отличие от артефактов, **не чистятся автоматически**:
обход стоит дорого и переживать автоочистку по счётчику прогонов не должен.

## Обход сайта

Сохранить одну страницу мало, когда вопрос стоит про сайт целиком: где дубли заголовков, куда
ведут битые ссылки, какие страницы закрыты от индексации. `crawl` обходит сайт по внутренним
ссылкам и складывает всё в архив, по которому потом можно спрашивать.

```sh
# запустить: управление возвращается сразу, обход идёт фоном
crawl --url https://example.ru/

# посмотреть прогресс
crawl --action status --site-id example-ru

# остановить (сработает и из другого процесса)
crawl --action stop --site-id example-ru
```

Обход **гибридный**. Сначала обычный HTTP-запрос: дёшево и показывает ровно то, что видит
поисковый робот, не исполняющий скрипты. Если ответ выглядит пустым — мало текста, нет `h1`,
пустой корневой контейнер SPA — страница переоткрывается в браузере. Расхождение между двумя
версиями само по себе находка: значит, контент появляется только после JS.

### Вежливость

По умолчанию включено всё сразу: `robots.txt` уважается, между запросами полсекунды паузы,
не больше 500 страниц и 5 уровней вглубь, только тот же хост. `Crawl-delay` из `robots.txt`
может увеличить паузу, но не уменьшить её.

> [!warning]
> `respectRobots: false` существует для своих стендов. Факт отключения записывается в манифест
> обхода и попадает в отчёт — по нему должно быть видно, что обход был невежливым, даже если
> смотрят его через полгода.

Адреса, запрещённые в `robots.txt`, не выбрасываются молча: они попадают в `skipped` вместе
с указанием страницы, которая на них сослалась. Иначе на вопрос «что у нас закрыто от индексации,
но залинковано изнутри» ответить нечем.

### Работа по архиву

```sh
# дубли заголовков — группы больше одной страницы
crawl_pages --site-id example-ru --group-by title

# что отвечает 404
crawl_pages --site-id example-ru --filter '{"status":404}'

# тонкий контент
crawl_pages --site-id example-ru --filter '{"maxWords":150}'

# страницы без описания
crawl_pages --site-id example-ru --filter '{"missing":["description"]}'

# селектор по всем сохранённым страницам сразу
crawl_query --site-id example-ru --select 'a[target="_blank"]:not([rel~="noopener"])' --attr href
```

`crawl_pages` отвечает списком страниц, `crawl_query` — списком найденных узлов с указанием
страницы. Это разные вопросы, поэтому и инструмента два. Оба всегда сообщают `total` и
`truncated`: выборка урезается, и об этом надо знать, а не делать вывод по первым пятидесяти
страницам из пятисот.

Разметку страниц эти инструменты не возвращают — только поля и ссылки. За разметкой в
`read_artifact` или прямо в файл зеркала.

### robots.txt и карта сайта

```sh
site_files --url https://example.ru/ --check '["https://example.ru/admin"]'
site_files --url https://example.ru/ --site-id example-ru   # сверить карту с обходом
```

Сверка показывает расхождения в обе стороны, и это разные диагнозы. Есть в карте, но не найдено
обходом — страница либо сирота, либо карта устарела. Найдено обходом, но нет в карте — карту
не обновили.

## Логин и куки

Внутри одной сессии куки и хранилища работают сами собой, но `browser_close` уносит их вместе
с контекстом. `browser_storage` позволяет сохранить состояние и вернуть его в новую сессию:

```sh
# залогинились руками через browser_act, сохранили
browser_storage --session ... --action export --name prod

# в любой следующей сессии
browser_open --url https://example.ru/lk --storage-state prod
```

Имя `prod` принимают все инструменты, которые открывают свою сессию, — `audit`, `seo_page`,
`page_save`, `web_vitals`.

> [!warning]
> Каталог `app/data/state/` содержит куки живых сессий. Он намеренно закрыт: не раздаётся
> через nginx и не читается ни `read_project_file`, ни `browser_route`. Не коммитьте его.

Отдельно стоит знать про границы: куки живут на контексте и видны сразу по всем доменам,
а `localStorage` и `sessionStorage` снимаются с **текущей страницы** — API уровня контекста
у них в Playwright нет. В ответе это указано полем `scopeNote`.

## Условия просмотра

Любую проверку можно запустить в конкретных условиях:

```sh
--browser chromium|firefox|webkit    движок (webkit ≈ Safari)
--viewport 375x812                   или mobile, mobile-sm, tablet, laptop, desktop, wide
--dark                               тёмная тема
--rtl                                справа налево (арабский, иврит)
--zoom 200                           страница увеличена вдвое
--text-zoom 200                      увеличен только шрифт
--pseudo                             текст длиннее на 40% — как после перевода
--forced-colors                      режим высокой контрастности Windows
--dpr 2                              экран Retina
```

`lt matrix` перемножает эти условия между собой: одним прогоном проверяется страница во всех
сочетаниях сразу.

Отдельно — доступ к странице, на картинку он не влияет и в именах эталонов не участвует:

```sh
--auth user:pass                     HTTP basic auth (логин в URL зашивать не надо:
                                     он потом лезет во все ссылки и имена файлов)
--header "Accept-Language: ru"       заголовок ко всем запросам
--host-map "site.local:172.20.0.5"   подменить разрешение имени — для стендов за vhost,
                                     когда сайт не отвечает без правильного Host
--hide ".cookie-notice,.chat"        убрать с кадра баннеры и всплывашки
```

## Отладка вёрстки

Четыре инструмента, которые агент использует, когда правка «не применилась» или блок
«куда-то пропал». Все работают в открытой сессии браузера.

**`matched_rules`** — все CSS-правила, матчащие элемент: селектор, специфичность, файл и
строка, и по каждому свойству кто победил, а кого перебили. Это ответ на вопрос, на который
вычисленные стили не отвечают: почему выиграло не ваше правило. Понимает псевдоэлементы
(`::before`), так что разбирает и затемнения-оверлеи. Работает только в chromium.

**`element_layers`** — почему элемента не видно и кто лежит сверху: порядок отрисовки,
цепочка стек-контекстов над элементом, перекрывающие соседи и что реально нарисовано в его
точках. Отдельно предупреждает про два классических случая: `z-index` на `position: static`
(не действует вовсе) и `z-index`, который считается внутри чужого стек-контекста, а не по
всей странице.

**`browser_style`** — вкатить свой CSS или JS поверх открытой страницы; патч переприменяется
после каждого перехода. Так правку проверяют на боевом или чужом стенде, ничего там не меняя:
добавили правило — сняли скриншот — сравнили с эталоном.

**`browser_route`** — правила на сетевые запросы: отрезать аналитику и чаты, из-за которых
страница не доходит до `load`; подменить таблицу стилей своей сборкой; подставить заглушки
вместо отсутствующих картинок; переписать адреса. В списке правил виден счётчик попаданий —
молчащее правило иначе не отличить от сработавшего.

Обработчики: `block`, `fulfill` (отдать свой `body`), `file` (отдать файл стенда),
`redirect` (увести все совпадения на один `url`), `rewrite` (заменить кусок адреса, сохранив
путь), `passthrough`.

`rewrite` — для случая, когда сайт отдаёт абсолютные ссылки боевого домена:

```jsonc
{ "pattern": "**/*",
  "handler": "rewrite",
  "from": "/^https?:\\/\\/site\\.ru/",   // подстрока или /…/flags
  "to": "http://nginx_local" }           // в замене работают $1, $2
```

Протокол при этом менять нельзя — `http` остаётся `http`. В `list` у правила два счётчика:
`hits` — сколько запросов попало под `pattern`, `rewrites` — сколько адресов реально
заменено. Если второй нулевой, `from` не совпадает.

## Снимки

Что попадает в кадр:

```sh
--selector ".product-card"           снять один элемент, а не всю страницу
--hide ".cookie-notice,.chat"        спрятать баннеры; место под ними остаётся,
                                     снимок сравним с эталоном
--isolate "*:nth-child(4),*:nth-child(5)"
                                     оставить только эти элементы, соседей убрать
                                     из потока — так снимают пару блоков рядом
--mask ".ads,.clock"                 закрасить живой контент
```

Во что кодировать — `--format png|jpeg|webp`, `--quality`, `--max-width`. По умолчанию
полноразмерный `png`. Для вставки в документ берите `webp` с `--max-width 1000`: файл выходит
на порядок легче.

У `visual_compare` формата и масштаба нет — эталоны сравниваются попиксельно.

Ленивые картинки догружаются сами, отдельных флагов не нужно.

## Визуальный справочник

`visual_guide` собирает инструкцию для тех, кто наполняет сайт: перечисленные блоки страницы,
снятые в нескольких ширинах, каждый со своими подписями.

```jsonc
{
  "url": "http://site.local/photo",
  "title": "Блоки фотоархива",
  "profiles": ["desktop", "mobile"],
  "items": [
    { "selector": "#y1952 > *:nth-child(3)",
      "title": "Горизонтальное расположение",
      "params": { "Расположение": "Горизонтальное", "Ширина текста": "300 px" } },

    { "selector": "#y1952",
      "title": "Наложение на соседний блок",
      "isolate": ["*:nth-child(4)", "*:nth-child(5)"],
      "note": "Показан вместе со следующим блоком — иначе эффекта не видно" }
  ]
}
```

На выходе один HTML со вшитыми картинками — пересылается вложением, папка с файлами рядом
не нужна. Ненайденный селектор оставляет в документе дырку и попадает в `warnings`;
остальные варианты собираются.

Отчёт матрицы тоже умеет вшивать картинки — `inlineImages`.

## Рецепты

**«Проверь, не сломалась ли вёрстка после моих правок»**

```sh
docker compose exec playwright lt compare --url http://nginx_myshop/ --name main
```

**«Сайт едет на телефоне»**

```sh
docker compose exec playwright lt audit --url http://nginx_myshop/ --viewport mobile --checks layout
```

Смотрите `overflowingElements` — это элементы, вылезшие за экран.

**«Страница прыгает при загрузке»**

```sh
docker compose exec playwright lt audit --url http://nginx_myshop/ --checks vitals
```

В `shifts` будет список блоков, которые сдвинули содержимое.

**«Как выглядит в Safari»**

```sh
docker compose exec playwright lt shot --url http://nginx_myshop/ --browser webkit
```

**«Проверь тёмную тему»**

```sh
docker compose exec playwright lt matrix --url http://nginx_myshop/ --schemes light,dark
```

**«Сайт долго грузится и проверка отваливается»**

```sh
docker compose exec playwright lt audit --url http://nginx_myshop/ --timeout 60000
```

Стенд не падает, если страница не догрузилась: проверит то, что отрисовано, и скажет об этом.

## Где лежат результаты

Всё внутри `app/data`:

- `artifacts/` — скриншоты, отчёты, карты отличий. Открываются на `http://127.0.0.1:8089/`
- `baselines/` — эталоны для сравнения. Их стоит держать в git
- `fixtures/` — тестовые страницы, в том числе ваши
- `sites/` — зеркала сохранённых страниц. Открываются на `http://127.0.0.1:8089/sites/`
- `state/` — сохранённые логины. Наружу не отдаётся и в git не кладётся

В ответе у каждого артефакта две ссылки. `url` — открыть в своём браузере. `internalUrl` —
подставить в `browser_goto`, если стенду нужно открыть собственный отчёт: снаружи и изнутри
контейнера адреса разные.

Артефакты копятся и чистятся сами: при заведении нового прогона всё старше последних
`ARTIFACTS_KEEP` прогонов удаляется. Почистить вручную:

```sh
docker compose exec playwright lt clean --keep 20
```

**`sites/` под автоочистку не попадает** — намеренно. Обход сайта стоит несопоставимо дороже
скриншота, и терять его от того, что рядом сняли полсотни кадров, нельзя. Удалять — руками.

## Если что-то не работает

**`lt: not found`** — контейнер ещё ставит зависимости. Дождитесь в логе строки
`команда lt готова`: `docker compose logs -f playwright`.

**Сайт не открывается по имени контейнера** — он в другой сети. Проверьте `docker network ls`
и подключите: `docker network connect имя_сети playwright_layout`.

**Страница отвечает 401** — она за HTTP-аутентификацией. Передайте `--auth user:pass`
(агенту — `auth` при открытии сессии). Зашивать логин в адрес не нужно: оттуда он расползается
по отчётам и именам файлов.

**На снимке пустые рамки вместо картинок** — медиа не загрузилось, хотя страница ответила `200`.
Чаще всего сайт отдаёт абсолютные адреса боевого домена, недостижимого со стенда. Проверьте
`warnings` в ответе перехода, дальше есть два пути:

- `--host-map "site.ru:172.20.0.5"` — если локальный сервер отвечает на том же пути;
- правило `browser_route` с `rewrite` — если путь надо переписать целиком.

**Сравнение показывает отличия, хотя ничего не меняли** — на странице живой контент: часы,
карусель, реклама. Закройте их маской:

```sh
docker compose exec playwright lt compare --url ... --name main --mask ".ads,.clock"
```

**Вместо букв квадраты на скриншоте** — не хватает шрифтов. Проверить:
`lt shot --url http://nginx_layout/fixtures/fonts.html` — там кириллица, эмодзи и иероглифы.
Если квадраты, пересоберите: `docker compose up -d --build`.

**Chromium падает на длинных страницах** — не хватает `/dev/shm`. Увеличьте
`PLAYWRIGHT_SHM_SIZE` в `.env` и пересоберите.

**Матрица съедает память** — каждый браузер весит сотни мегабайт. Уменьшите
`--concurrency 1`.

**Проверка HTML говорит «vnu недоступен»** — не поднят контейнер `vnu`. Стенд продолжит
работать со встроенным валидатором, но правил будет меньше.

**Сайт отвечает 404 или отдаёт не тот проект** — он смотрит на `Host`, а вы ходите по IP.
Заголовком это не чинится, Chrome его игнорирует; нужен `--host-map "site.local:172.20.0.5"`.

**Страница за паролем** — `--auth user:pass`. Логин внутри URL тоже сработает, но потом
попадёт в ссылки, заголовки и имена артефактов.

## Настройки

Всё в `app/.env`.

| Параметр | Зачем менять |
|---|---|
| `EXTERNAL_ACCESS` | порт отчётов на хосте, по умолчанию `8089` |
| `MCP_ACCESS` | порт MCP напрямую, мимо nginx |
| `TRAEFIK_DOMAIN` | домен стенда, по умолчанию `layout.localhost` |
| `PLAYWRIGHT_SHM_SIZE` | память под Chromium, по умолчанию 2 ГБ |
| `PUBLIC_BASE_URL` | база ссылок на артефакты в ответах агенту |
| `LT_LANG` | язык описаний инструментов: `ru`, `en`, `auto` |
| `LT_UPDATE_CHECK` | `0` выключает проверку обновлений — для контуров без выхода наружу |
| `LT_IMAGE_TAG` | тег собранного образа; по нему проверка понимает, что тянуть |
| `LT_UPDATE_REPO`, `LT_UPDATE_IMAGE` | откуда брать обновления — для форков |

Версии образов зафиксированы намеренно — стенд должен давать одинаковый результат сегодня и
через полгода. `PLAYWRIGHT_VERSION` менять только вместе с версией пакета `playwright` в
`app/data/package.json`: браузеры вшиты в образ и по другой версии не найдутся.

## Обновления

При запуске стенд один раз спрашивает у GitHub, какой релиз последний, и сравнивает с собой.
Если версия новее — агент видит это в описании сервера сразу при подключении, а подробный
порядок действий лежит в `stand_info`, поле `update`.

Проверка ничего не блокирует. GitHub может лежать, ограничивать по частоте или быть недоступен
вовсе — на это отведено четыре секунды и перехват любых отказов, после чего стенд работает
дальше на текущей версии, а в ответе стоит «неизвестно», а не ошибка. Результат кэшируется на
шесть часов: неавторизованный лимит GitHub — 60 запросов в час на адрес, а сервер
перезапускается легко.

Обновиться можно двумя путями.

```sh
# из готового образа
docker pull ghcr.io/cat-of-summer/layouttesting---mcp-playwright-package:0.0.5
# подставить тег в BUNDLE_IMAGE в .env и поднять заново
docker compose up -d

# из исходников
git pull && git submodule update --remote
dockerbundle generate
docker compose up -d --build
```

Артефакты, эталоны, зеркала и сохранённые логины лежат в томах и обновление переживают.

> [!note]
> Версий две, и путать их не надо. В `package.json` лежит версия кода, а `docker pull` требует
> тег образа — совпадать они не обязаны. Поэтому сравнение идёт с `LT_IMAGE_TAG`, если сборка
> его задала. Без него стенд сравнивал бы релиз с версией кода и мог бы промолчать об
> обновлении.

Выключается целиком: `LT_UPDATE_CHECK=0`. В закрытом контуре запрос всё равно упрётся в
таймаут, и четыре секунды на старте платятся впустую.

## Язык

Описания инструментов читает не человек, а модель — и читает на том языке, на котором к ней
обращаются. Русские описания на англоязычной задаче находятся хуже. Язык переключается
переменной `LT_LANG`:

```sh
LT_LANG=ru     # по умолчанию
LT_LANG=en
LT_LANG=auto   # посмотреть на LANG/LC_ALL
```

`auto` — подстраховка, а не основной способ. В контейнере `LANG` обычно `C.UTF-8` или пуст, и
о языке задачи это не говорит ничего: тогда берётся русский. На машине разработчика авто
работает. Какой язык выбран и почему — видно в `stand_info`, поле `language`.

## Из чего собран

Модули [docker_toolkit](https://github.com/cat-of-summer/docker_toolkit) — `nginx`,
`playwright`, `vnu`, `network`, `traefik` — запечены в проект: подмодулей нет, всё
поднимается как есть. Внутри: Playwright с тремя браузерными движками, MCP-сервер на Node,
nginx для раздачи отчётов, Nu HTML Checker (валидатор W3C).

### Как собирается образ

`nginx`, `playwright` и `vnu` сводит в один образ
[dockerbundle](https://github.com/cat-of-summer/DockerBundle---python): он читает те же
compose-файлы, что и стенд, и раскладывает сервисы по supervisord. Всё, что нужно знать
сборщику, — в одном файле `docker-bundle.yml`: источники, отбор сервисов, рецепты трёх
сервисов и разрешение конфликтов между пакетами. Результат ложится в `dist/` и **в git не
хранится**: CI собирает его на каждом прогоне. Иначе в дереве жили бы и исходник, и
результат — с конфликтами в сгенерированных файлах и риском однажды собрать образ из
того, чего в `docker-bundle.yml` уже нет.

Генератор в репозитории тоже не лежит: CI ставит его из релиза по закреплённому тегу, а
локально он ставится тем же скриптом.

```sh
curl -fsSL https://raw.githubusercontent.com/cat-of-summer/DockerBundle---python/vX.Y.Z/install.sh | sh -s -- vX.Y.Z
dockerbundle generate
```

Тег обязателен: обновление генератора должно быть видно как правка переменной CI, а не
менять поведение сборки молча. Бинарь — ELF под Linux; на Windows запускать через WSL,
хостовый Git Bash его не выполнит.

`traefik` и `network` в бандл не входят: они помечены `mode: off`. traefik живёт снаружи и
переживает пересборку стенда, а заглушка `network` не нужна — сеть заводит сам compose.
Без traefik стенд доступен по опубликованному порту; маршрутизация по домену появляется
только когда прокси поднят рядом.

Отличия запечённого стенда от сборки из исходников — по существу два: код и зависимости
устанавливаются на сборке образа, а не при старте контейнера; и сервисы делят сетевое
пространство, поэтому внутри обращаются друг к другу по `127.0.0.1`.
